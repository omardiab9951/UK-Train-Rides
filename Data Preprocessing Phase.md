# Data Preprocessing Phase

## 1. Purpose and data flow

The preprocessing work prepares ticket-transaction data for analysis and downstream modeling. The project describes this flow:

```text
raw railway.csv  →  cleaned_railway.csv  →  processed_railway.csv
```

Each version contains 31,653 rows. The files differ in their columns and representations: the raw file preserves source fields, the cleaned file standardizes and combines selected fields, and the processed file contains mostly numerical or encoded features.

The project includes both a cleaning script and notebooks used for investigation. These do not represent exactly the same workflow: the script is the stated route to the cleaned CSV, while the cleaning notebook is described as an exploratory workspace. This distinction should be kept in mind when reproducing the pipeline.

## 2. Cleaning script and cleaned dataset

The script `src/clean.py` performs the documented cleaning steps:

1. Loads the raw CSV.
2. Removes duplicate full rows (none were found in the original dataset, so this does not reduce the reported row count).
3. Combines purchase date and time into `Purchase Datetime`.
4. Combines journey date and departure time into `Journey Datetime`.
5. Removes the original date and time columns and ID columns.
6. Standardizes delay-reason labels.
7. Converts blank delay reasons to `No Delay`.
8. Converts missing Railcard values to `No Railcard`.
9. Saves `data/cleaned/cleaned_railway.csv`.

The cleaned output has 31,653 rows and 14 columns. It retains purchase type, payment method, Railcard, ticket type, price, departure and arrival stations, scheduled and actual arrival times, journey status, standardized delay reason, refund request, and the two combined datetime fields.

### Important schema decision

The script removes `Ticket Class`, even though the raw data contains it and the EDA analyzes it. Therefore, the cleaned dataset cannot support analyses requiring Standard versus First Class unless the cleaning pipeline is changed to retain that field. This should be decided explicitly before dashboard development or modeling.

### Category standardization

The documented mappings include:

| Original value | Standardized value |
|---|---|
| Staffing | Staff Shortage |
| Weather | Weather Conditions |
| Technical | Technical Issues |
| Blank delay reason | No Delay |

The notes indicate that the exact standardized labels should be verified against the actual output; the raw dataset's delay-reason values include related variants such as `Weather Conditions` and `Technical Issue`.

## 3. Cleaning notebook as an exploratory workspace

`02_Cleaning.ipynb` is described as an experimental cleaning and feature-selection workspace rather than the main reproducible cleaning pipeline. It contains reusable ideas and helper functions for:

- Converting date and numeric fields
- Classifying variables and inspecting distributions
- Filling missing values
- Correcting inconsistent category names
- Encoding categorical variables
- Selecting features using statistical relationships

It also checks possible logical issues, including the same departure and arrival station, negative prices, purchases after the journey, and inconsistent delay-reason labels.

The notebook includes feature-selection work focused on `Refund Request`, using chi-square tests for categorical variables and mutual information for numeric variables. Its original workflow exports a cleaned Excel file. The project notes mention naming and syntax-quality issues in some helper code, so the notebook should be tested before it is relied on as a production pipeline. Its outputs should not be assumed identical to the CSV generated by `src/clean.py`.

## 4. Data-quality investigation and review flags

`03_Preprocessing.ipynb` investigates unusual values and creates analytical features. The project generally retains flagged records rather than deleting or changing them automatically, because there is not enough external evidence to determine whether they are errors.

### Price outliers

The notebook uses the interquartile range (IQR) method to identify unusual prices. Overall price analysis identified 1,555 potential outliers. Group-based analysis found more because price distributions vary across ticket categories. Some high prices recur on particular routes, suggesting that they may reflect valid route pricing. The values are retained.

### Delays

Delay minutes are calculated by comparing scheduled and actual arrival times. The notebook reports 130 delays above the calculated IQR threshold and 18 records marked `Delayed` despite a calculated delay of zero. These records are retained for review rather than automatically corrected.

### Purchase lead time

Lead time is the difference between purchase datetime and journey datetime. The analysis checks purchases made after departure and unusually short lead times for Advance tickets. It flags 456 Advance tickets bought less than 12 hours before departure. These records are retained.

### Scheduled journey duration

Scheduled journey duration is calculated, with journeys crossing midnight adjusted accordingly. The London Paddington to London Waterloo route has 68 records with a suspicious 90-minute scheduled duration. These are flagged but retained.

### Night departures

There are 4,023 journeys departing between midnight and 4:59 AM (about 12.7% of the records). This pattern is flagged as unusual for review, not automatically labeled incorrect.

### Combined flags

In total, 4,236 records (about 13.4% of the dataset) receive at least one review flag. A record may have more than one flag, so this total is not the sum of the individual issue counts. The rows are not deleted or modified solely because they are flagged.

## 5. Feature engineering and transformations

The preprocessing notebook creates or investigates features such as:

- Day of week and month
- Departure hour and a weekend indicator
- Scheduled journey duration
- Delay minutes
- Route
- Lead time
- Revenue per ticket and revenue per ride
- Number of tickets associated with the same ride
- Night-departure indicator

It also examines skewness in numerical fields such as price, lead time, revenue per ride, tickets per ride, and delay. Transformed versions of some fields are created while preserving the originals. These transformations are intended for downstream analysis or modeling, but the provided project notes do not specify every formula or transformation parameter.

## 6. Processed dataset

`data/processed/processed_railway.csv` has 31,653 rows and 30 columns. It is intended for numerical analytical and modeling workflows. It includes encoded purchase types, payment methods, Railcard categories, ticket types, delay reasons, journey statuses, station fields, and refund-request values, alongside transformed price and engineered values such as weekend, night-departure, lead time, delay, and journey duration.

The original category labels are mostly no longer present in this file. The precise encodings, reference mappings, transformation formulas, and model-specific preparation are not documented in the supplied notes. Therefore, processed values should not be interpreted as original business values without consulting the raw or cleaned data and the transformation code.

## 7. Meaningful blanks and interpretation

Not every blank indicates a data error. For example, actual arrival time can be blank for cancelled journeys, and delay reason can be blank for an on-time journey. `None` in the Railcard field means no Railcard was used. When preprocessing, these cases should be handled according to their meaning rather than filled indiscriminately.

Similarly, a refund request does not confirm that a refund was approved or paid, and ticket-price sums are recorded sales value before refunds—not confirmed net revenue or profit. The source currency is unspecified; use “price units” unless the source is verified.

## 8. Current limitations and recommended checks

Before treating preprocessing as final or using the processed data in a model or dashboard, verify:

1. **Schema consistency:** Decide whether `Ticket Class` should be retained in the cleaned file, especially because the EDA uses it.
2. **Reproducibility:** Run `src/clean.py` from a clean environment and confirm its output schema, row count, category labels, and missing-value behavior.
3. **Notebook versus script:** Document which workflow is authoritative and whether the notebook's Excel output is still used.
4. **Encoding and transformation definitions:** Record category mappings, scaling or skew transformations, formulas, units, and any fitted parameters. For predictive modeling, fit transformations on training data only to avoid data leakage.
5. **Review flags:** Preserve the original values and keep flags separate unless external evidence supports correction or removal.
6. **Target and feature design:** Define the modeling question and target before selecting or encoding features; feature-selection results focused on `Refund Request` do not automatically apply to other targets.
7. **Business interpretation:** Avoid claims about passengers, actual boardings, confirmed refunds, profit, or live UK railway operations that the data cannot establish.
